# 豆包生成需求事实源

> 状态：当前有效（唯一业务事实源）  
> 适用范围：Quota-Flow 桌面端豆包 WebView 生成、分镜生成、多账号调度、确认交互、窗口生命周期、失败恢复与诊断日志。  
> 优先级：用户当前明确要求 > 本文 > 旧计划/旧注释/历史实现。

## 1. 为什么建立本文

豆包生成需求长期以零碎对话逐步增加，历史提交曾把批量、兜底、账号调度、上传等待、自动确认和窗口生命周期混在一次修改中，导致已稳定行为被覆盖。本文将已确认需求整理为可测试合同，后续改动必须逐项对照，禁止从旧代码反推需求。

## 2. 核心生命周期合同

### 2.1 唯一自动关窗条件

豆包**生成窗口**只有在程序明确识别到“相对提交前 baseline 的本次新增视频 URL”时才允许自动关闭。

以下情况一律不得自动关闭，必须显示并保留原生成窗口，由用户手动处理或关闭：

- 页面加载失败；
- 输入框/DOM 未找到或页面结构变化；
- 图片读取、上传或上传完成检测失败；
- 提示词填写或提交检测失败；
- 豆包要求确认参数；
- 风控、验证码、安全确认、免责声明；
- 内容拒绝或限流；
- 等待视频超时；
- 用户取消；
- 登录态失效；
- baseline 采集失败；
- 任何未知错误。

### 2.2 baseline 规则

- 提交前必须采集当前页面已有视频 URL 集合。
- 生成后只接受不在 baseline 中的新增 URL。
- baseline 采集失败不应阻止主提示词提交；必须立即显示并保留原生成窗口。继续提交后不得自动认定或下载页面已有视频、不得自动关窗或自动换号，并记录 baseline 失败日志。已有人工兜底入口仍可使用，不把它改造成主流程的新阻塞条件。

## 3. 提交与确认合同

### 3.1 主提示词提交

- 文生视频可使用清空后填入主提示词的脚本。
- 图生视频必须保留已经上传的图片节点/chip，再追加提示词并提交。
- 页面脚本只负责把非空提示词写入并聚焦输入框；Enter 必须由 Electron 主进程通过 `webContents.sendInputEvent` 发送真实输入事件，不再使用页面内合成 `KeyboardEvent`。
- 不再以“输入框在固定时间内清空”“提示词前缀从 DOM 消失”或“整页正文出现提示词”作为提交成功硬门槛；这些信号在不同系统和页面渲染时序下不稳定。
- 原生 Enter 已发出后进入等待/人工接管流程；只有页面明确出现本次新增发送失败信号、明确网络失败或其他既有确定失败信号时才判失败。
- 用户在原生 Enter 发出后主动关闭可见生成窗口，表示主动结束客户端追踪并继续下一段，属于正常操作；释放本轮锁，不自动换号、不标记账号失效。

### 3.2 豆包确认回复

“确认回复”指：主提示词已经成功发送后，豆包在聊天回复中要求用户再次确认参数，例如：

- “确认后我再开始生成视频”；
- “确认以上参数”；
- “视频生成参数确认”。

这一步不是主提示词提交，也不是上传图片。确认回复必须：

- 使用独立的追加文本脚本；
- 在当前输入框末尾追加“确认，直接开始生成”并按 Enter；
- 不得清空 ProseMirror；
- 不得重置图片、主提示词或当前会话上下文；
- 自动确认失败时显示并保留原窗口，交用户人工二次确认。
- 只响应主提示词提交后新出现的确认请求；历史聊天中的确认文案不得触发本次自动确认或人工提示。

`0f8a663` 恢复的就是这一“主提示词提交之后的豆包二次确认回复脚本”，不是恢复全部窗口生命周期。

## 4. 多账号调度合同

### 4.1 自动模式允许换号的白名单

只有明确的账号级故障允许自动尝试下一账号：

- 账号明确未登录/登录态失效；
- Cookie 明确失效或解密失败；
- 当前账号明确额度或生成次数耗尽/达到上限。

### 4.2 禁止换号

以下错误与账号无直接证据关联，不得换号：

- 页面结构变化、输入框未找到；
- 图片上传或上传检测失败；
- 提示词填写/提交失败；
- 风控、验证码、内容拒绝、限流；
- 等待视频 URL 超时；
- baseline 失败；
- 网络/DOM/未知错误；
- 用户取消。

### 4.3 手工指定账号

- 手工指定账号永不自动回退其他账号。
- 失败后保留该账号生成窗口和对应 partition 现场。

## 5. 账号 partition 合同

- 生成 partition 固定为 `persist:qf-p:doubao:<keyId>`。
- 人工“打开豆包”必须使用生成时同一 `keyId`。
- 日志、进度文件和失败恢复必须持久化 `accountId`。
- 不得在失败后打开另一个账号或默认 partition 冒充原现场。

## 6. 图片上传合同

- 用户已在真实豆包网页确认 10 张图片可以正常触发视频生成；当前 10 张能力保持不变，不得根据旧文档口径擅自降为 9 张。
- 已稳定等待策略：触发文件 change/input 后，至少等待约 9.75 秒；此后必须连续多次确认页面无上传/压缩/处理状态，再等待 2 秒并复检。2 秒内状态重新出现时继续等待，禁止把一次短暂文案空窗当成上传完成。
- 禁止未经真实页面验证擅自缩短为快速稳定窗口，也不得仅靠一次“无处理中”采样提前提交。
- 上传检测结果必须记录：耗时、输入文件数、实际 input 文件数、最后检测到的处理中状态，以及可获得的上传/提交网络失败分类与 HTTP 状态；日志不得记录完整 URL、响应体或素材内容。
- 页面出现相对提交前新增的“发送失败/重发”状态，或捕获到本次上传/提交请求明确失败时，当前生成应立即返回失败并释放客户端生成锁；保留原豆包窗口交人工重发，不换号、不标记账号失效，不继续等待 15 分钟。
- 上传检测失败不得提交、不得换号、不得关闭窗口。
- 红色叹号的具体来源可能是网络、上传方式、素材或豆包页面状态；没有真实响应证据时只记录分类，不猜测具体根因。
- 程序不得把豆包网页原本没有超时的上传/提交 XHR 擅自改成固定 30 秒超时；网络慢或代理环境下由网页自身决定请求生命周期，失败时只记录可获得的状态并保留原窗口人工处理。
- macOS 慢渲染现场中，页面标题和导航已加载但输入框/用户信息可能暂未出现。首次页面就绪判断不得单次未命中就判永久失败；应在有界时间内轻量轮询，只认“可见输入框”或“可见视频生成入口”为页面就绪，明确登录墙可提前判未登录。仅 `hasUserInfo=false` 不能单独判账号失效；到期仍无可操作节点时按页面未就绪失败、保留原窗口、不换号。

### 6.1 同账号窗口互斥

- 不同账号允许各自打开豆包窗口并由用户手动并行操作，账号间 partition 保持隔离。
- 同一账号只允许存在一个由生成/人工兜底管理的豆包主操作窗口。已有窗口仍存活时，新的自动生成不得再创建窗口或覆盖 registry 引用；应聚焦原窗口并提示用户处理或关闭后重试。
- 豆包主操作窗口发起指向豆包聊天页的 `window.open` 时不得创建第二个豆包主页面，应继续保留并聚焦原窗口；必要的非豆包登录/验证弹窗保持现有放行策略，不在本轮扩大重构。
- 用户手动关闭原豆包主操作窗口即表示结束本次生成：当前页面等待必须立即返回，客户端任务锁、生成启动锁和窗口 registry 必须随本轮调用结束释放；之后再次生成才允许创建一个新窗口。
- 自动生成仍保持现有串行策略；本规则不限制不同账号的人工并行操作。
- “进入官网”窗口属于独立入口，本轮不合并窗口体系，但不得覆盖生成/人工兜底窗口引用。

## 7. 日志合同

Windows 日志位置：`Quota-Flow.exe` 同目录的 `qf-generation.log`。

每次生成至少记录：

- jobId、shot index、模式、时长；
- 每次账号尝试的 accountId、账号名、round、partition；
- WebView 阶段；
- baseline 是否成功及历史视频数量；
- 上传开始/结果/诊断；
- 提交开始/结果；
- 确认请求及自动/人工处理结果；
- 视频新增检测；
- 窗口“关闭/保留”决定及原因；
- 换号/不换号决定及原因；
- 最终结果、下载结果和状态回写异常。

禁止记录：

- Cookie、token、API key、encrypted_key；
- 完整签名 URL；
- 完整提示词或编辑器文本片段；
- 其他用户敏感内容。

## 8. 失败恢复合同

- 失败任务必须写进度文件，并保留 jobId/accountId/remoteUrl（如有）。
- 有 remoteUrl 时允许补下载；补下载对应的视频已经生成，补下载成功必须按原 job 的账号、团队归属和 cost_amount 幂等补做额度结算，不得重复扣费。
- 无 remoteUrl 时允许用同账号 partition 打开豆包人工处理。
- 分镜词解析到客户端后允许在分镜界面临时修改；修改只保存在当前客户端状态，不回写来源 markdown。点击逐段生成或后续批量生成时，必须把该分镜界面的最新文本同步到豆包。
- 分镜词解析器必须兼容已量产的新式段号与字段结构（如 `E01-V01｜标题｜00:00—00:15｜15秒`、`动作链：`、`D001｜时间｜ROLE：台词`），同时保持旧 `V001` 格式兼容；不得要求上游批量退回旧格式。推荐产出规范见 `全剧分镜提示词稳定产出规范.md`。
- 只有明确持久化了 accountId 才显示“打开豆包”；不得用默认 partition 冒充失败账号现场。
- 用户取消和主进程异常也必须写失败进度；已选账号后取消必须保留 accountId。
- 视频 URL 已取得后即使额度结算或状态回写失败，也必须在失败返回和进度文件中保留 jobId/accountId/remoteUrl，允许后续补下载。
- 同一分镜开始新一轮生成前必须同时清除前端状态和 `.storyboard-progress.json` 中上一轮的 jobId/remoteUrl/accountId/videoPath；旧视频文件不删除，但 `pending` 进度必须优先于磁盘文件，未知失败不得把旧视频或旧账号恢复为本轮结果。
- 进度清理及后续生成/下载/兜底状态回写失败都必须返回失败并提示，不得假装成功。
- 已存在的进度 JSON 无法解析时必须拒绝覆盖，禁止清空其他分镜的审计记录。
- 正常生成主流程只接受相对提交前记录新出现的视频。
- 生成失败后不再后台自动拉取，避免页面历史延迟加载、虚拟列表或签名 URL 变化造成静默错绑。
- 人工点击“打开豆包→下载最新/选视频”处理页面现有视频，不得反过来改变或阻塞正常提交链路。

## 9. 测试与发布门禁

### 9.0 当前批量开放状态

- 当前发布版本先走通普通逐段生成，批量生成按钮置灰并标注“暂未开放”。
- 批量底层逻辑不得删除或放任失效：保持严格串行、`autoConfirm=true`、失败不后台自动拉取、账号/窗口/日志规则与逐段流程一致。
- 任务进度区域必须显示批量当前状态；待普通流程完成 Windows 真实豆包验收后，再单独进行批量验收并开放入口。

### 9.1 本轮测试范围

- 本轮新增行为测试只覆盖豆包生成与豆包账号调度。
- 千问、元宝、Dola 暂不新增业务行为测试。
- 涉及共用调度文件时必须做隔离检查：豆包新策略只能在 `providerId === 'doubao'` 路径生效，其他厂商继续执行原有逻辑，不得因本轮改动改变其既有行为。

任何涉及 `webview-engine.ts`、`dispatch.ts`、账号选择、确认、上传、窗口生命周期的修改，发布前必须：

1. 先写失败回归测试；
2. 覆盖允许和禁止的状态转换；
3. `pnpm test` 全绿；
4. desktop typecheck/build 通过；
5. `git diff --check` 通过；
6. 搜索所有生成主流程 `win.destroy()`，确认只有视频成功路径可自动关闭；
7. 独立 Spec Reviewer 对照本文逐项审查；
8. 独立 Quality Reviewer 审查代码与日志脱敏；
9. Windows + 豆包真实人工验证通过后才能声称修复并打包。

## 10. 需求变更流程

### 10.1 默认模型

- 豆包默认模型为 `Seedance 2.0 Fast`，`Seedance 2.0 Mini` 保留供用户手动切换。
- 普通生成页、创作中心重新生成和分镜生成必须复用同一个默认模型常量，禁止各入口分别写死默认值。
- 页面模型选择器应用失败时沿用既有人工可见窗口策略，不附带扩大为新的自动换号或窗口销毁行为。
- 2026-11-16 已由用户在 Windows 真实豆包环境验证当前前台窗口生成流程可用；本轮发布仅记录验收与补齐默认模型回归门禁，不改 WebView 主流程。

新增或修改需求时必须同批完成：

1. 先更新本文并标注变化；
2. 更新/新增测试；
3. 再修改生产代码；
4. 更新版本需求审计；
5. 独立审查；
6. 验证后提交。

禁止只改代码不更新事实源，也禁止以历史实现覆盖本文已经明确的用户要求。
