# 豆包生成需求事实源

> 状态：当前有效（唯一业务事实源）  
> 适用范围：Quota-Flow 桌面端豆包 WebView 生成、分镜生成、多账号调度、确认交互、窗口生命周期、失败恢复与诊断日志。  
> 优先级：用户当前明确要求 > 本文 > 旧计划/旧注释/历史实现。

## 1. 为什么建立本文

豆包生成需求长期以零碎对话逐步增加，历史提交曾把批量、兜底、账号调度、上传等待、自动确认和窗口生命周期混在一次修改中，导致已稳定行为被覆盖。本文将已确认需求整理为可测试合同，后续改动必须逐项对照，禁止从旧代码反推需求。

## 2. 核心生命周期合同

### 2.1 唯一自动关窗条件

豆包**生成窗口**只有在程序明确识别到“相对提交前 baseline 的本次新增视频 URL”时才允许自动关闭。

以下情况一律不得自动关闭，必须显示并保留原生成窗口，由用户手动处理或关闭：

- 页面加载失败；
- 输入框/DOM 未找到或页面结构变化；
- 图片读取、上传或上传完成检测失败；
- 提示词填写或提交检测失败；
- 豆包要求确认参数；
- 风控、验证码、安全确认、免责声明；
- 内容拒绝或限流；
- 等待视频超时；
- 用户取消；
- 登录态失效；
- baseline 采集失败；
- 任何未知错误。

### 2.2 baseline 规则

- 提交前必须采集当前页面已有视频 URL 集合。
- 生成后只接受不在 baseline 中的新增 URL。
- baseline 采集失败不应阻止主提示词提交；必须立即显示并保留原生成窗口。继续提交后不得自动认定或下载页面已有视频、不得自动关窗或自动换号，并记录 baseline 失败日志。已有人工兜底入口仍可使用，不把它改造成主流程的新阻塞条件。

## 3. 提交与确认合同

### 3.1 主提示词提交

- 文生视频可使用清空后填入主提示词的脚本。
- 图生视频必须保留已经上传的图片节点/chip，再追加提示词并提交。
- 提交脚本必须返回可验证结果；无法确认提交时按提交失败处理，保留窗口。

### 3.2 豆包确认回复

“确认回复”指：主提示词已经成功发送后，豆包在聊天回复中要求用户再次确认参数，例如：

- “确认后我再开始生成视频”；
- “确认以上参数”；
- “视频生成参数确认”。

这一步不是主提示词提交，也不是上传图片。确认回复必须：

- 使用独立的追加文本脚本；
- 在当前输入框末尾追加“确认，直接开始生成”并按 Enter；
- 不得清空 ProseMirror；
- 不得重置图片、主提示词或当前会话上下文；
- 自动确认失败时显示并保留原窗口，交用户人工二次确认。
- 只响应主提示词提交后新出现的确认请求；历史聊天中的确认文案不得触发本次自动确认或人工提示。

`0f8a663` 恢复的就是这一“主提示词提交之后的豆包二次确认回复脚本”，不是恢复全部窗口生命周期。

## 4. 多账号调度合同

### 4.1 自动模式允许换号的白名单

只有明确的账号级故障允许自动尝试下一账号：

- 账号明确未登录/登录态失效；
- Cookie 明确失效或解密失败；
- 当前账号明确额度或生成次数耗尽/达到上限。

### 4.2 禁止换号

以下错误与账号无直接证据关联，不得换号：

- 页面结构变化、输入框未找到；
- 图片上传或上传检测失败；
- 提示词填写/提交失败；
- 风控、验证码、内容拒绝、限流；
- 等待视频 URL 超时；
- baseline 失败；
- 网络/DOM/未知错误；
- 用户取消。

### 4.3 手工指定账号

- 手工指定账号永不自动回退其他账号。
- 失败后保留该账号生成窗口和对应 partition 现场。

## 5. 账号 partition 合同

- 生成 partition 固定为 `persist:qf-p:doubao:<keyId>`。
- 人工“打开豆包”必须使用生成时同一 `keyId`。
- 日志、进度文件和失败恢复必须持久化 `accountId`。
- 不得在失败后打开另一个账号或默认 partition 冒充原现场。

## 6. 图片上传合同

- 已稳定等待策略：触发文件 change/input 后，至少等待约 9.75 秒；确认页面不再显示上传/压缩/处理状态后再等待 2 秒。
- 禁止未经真实页面验证擅自缩短为快速稳定窗口。
- 上传检测结果必须记录：耗时、输入文件数、实际 input 文件数、最后检测到的处理中状态。
- 上传检测失败不得提交、不得换号、不得关闭窗口。

## 7. 日志合同

Windows 日志位置：`Quota-Flow.exe` 同目录的 `qf-generation.log`。

每次生成至少记录：

- jobId、shot index、模式、时长；
- 每次账号尝试的 accountId、账号名、round、partition；
- WebView 阶段；
- baseline 是否成功及历史视频数量；
- 上传开始/结果/诊断；
- 提交开始/结果；
- 确认请求及自动/人工处理结果；
- 视频新增检测；
- 窗口“关闭/保留”决定及原因；
- 换号/不换号决定及原因；
- 最终结果、下载结果和状态回写异常。

禁止记录：

- Cookie、token、API key、encrypted_key；
- 完整签名 URL；
- 完整提示词或编辑器文本片段；
- 其他用户敏感内容。

## 8. 失败恢复合同

- 失败任务必须写进度文件，并保留 jobId/accountId/remoteUrl（如有）。
- 有 remoteUrl 时允许补下载；补下载对应的视频已经生成，补下载成功必须按原 job 的账号、团队归属和 cost_amount 幂等补做额度结算，不得重复扣费。
- 无 remoteUrl 时允许用同账号 partition 打开豆包人工处理。
- 分镜词解析到客户端后允许在分镜界面临时修改；修改只保存在当前客户端状态，不回写来源 markdown。点击逐段生成或后续批量生成时，必须把该分镜界面的最新文本同步到豆包。
- 只有明确持久化了 accountId 才显示“打开豆包”；不得用默认 partition 冒充失败账号现场。
- 用户取消和主进程异常也必须写失败进度；已选账号后取消必须保留 accountId。
- 视频 URL 已取得后即使额度结算或状态回写失败，也必须在失败返回和进度文件中保留 jobId/accountId/remoteUrl，允许后续补下载。
- 同一分镜开始新一轮生成前必须同时清除前端状态和 `.storyboard-progress.json` 中上一轮的 jobId/remoteUrl/accountId/videoPath；旧视频文件不删除，但 `pending` 进度必须优先于磁盘文件，未知失败不得把旧视频或旧账号恢复为本轮结果。
- 进度清理及后续生成/下载/兜底状态回写失败都必须返回失败并提示，不得假装成功。
- 已存在的进度 JSON 无法解析时必须拒绝覆盖，禁止清空其他分镜的审计记录。
- 正常生成主流程只接受相对提交前记录新出现的视频。
- 生成失败后不再后台自动拉取，避免页面历史延迟加载、虚拟列表或签名 URL 变化造成静默错绑。
- 人工点击“打开豆包→下载最新/选视频”处理页面现有视频，不得反过来改变或阻塞正常提交链路。

## 9. 测试与发布门禁

### 9.0 当前批量开放状态

- 当前发布版本先走通普通逐段生成，批量生成按钮置灰并标注“暂未开放”。
- 批量底层逻辑不得删除或放任失效：保持严格串行、`autoConfirm=true`、失败不后台自动拉取、账号/窗口/日志规则与逐段流程一致。
- 任务进度区域必须显示批量当前状态；待普通流程完成 Windows 真实豆包验收后，再单独进行批量验收并开放入口。

### 9.1 本轮测试范围

- 本轮新增行为测试只覆盖豆包生成与豆包账号调度。
- 千问、元宝、Dola 暂不新增业务行为测试。
- 涉及共用调度文件时必须做隔离检查：豆包新策略只能在 `providerId === 'doubao'` 路径生效，其他厂商继续执行原有逻辑，不得因本轮改动改变其既有行为。

任何涉及 `webview-engine.ts`、`dispatch.ts`、账号选择、确认、上传、窗口生命周期的修改，发布前必须：

1. 先写失败回归测试；
2. 覆盖允许和禁止的状态转换；
3. `pnpm test` 全绿；
4. desktop typecheck/build 通过；
5. `git diff --check` 通过；
6. 搜索所有生成主流程 `win.destroy()`，确认只有视频成功路径可自动关闭；
7. 独立 Spec Reviewer 对照本文逐项审查；
8. 独立 Quality Reviewer 审查代码与日志脱敏；
9. Windows + 豆包真实人工验证通过后才能声称修复并打包。

## 10. 需求变更流程

新增或修改需求时必须同批完成：

1. 先更新本文并标注变化；
2. 更新/新增测试；
3. 再修改生产代码；
4. 更新版本需求审计；
5. 独立审查；
6. 验证后提交。

禁止只改代码不更新事实源，也禁止以历史实现覆盖本文已经明确的用户要求。
